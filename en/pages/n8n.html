n8n — AI Automation

Workflow orchestration · VM300 · Docker · external PostgreSQL

Level: Intermediate
VM300 is an application VM dedicated to n8n: it runs automation workflows, delegates persistence to a services VM (PostgreSQL), and consumes the AI APIs of a separate GPU VM. This separation of application / data / compute lets each component evolve, be maintained and backed up on its own lifecycle.
✅ Deployed state
  • Ubuntu Server 24.04 LTS · Docker Engine + Compose
  • n8n 2.32.6 — pinned official image
  • Single instance, standard mode, without Redis
  • External PostgreSQL — encrypted connection, strong authentication
  • Remote Ollama API consumed by a validated workflow
  • Interface published over HTTPS by the shared reverse proxy
  • Persistence verified after container recreation and restart
🔒 Security of the current state
  • Application port kept on the internal network, public interface exposed only over HTTPS
  • System filtering + controlled Docker publishing
  • Secrets and encryption key outside Compose and outside Git
  • Pinned application image
  • Dedicated PostgreSQL database and role, encrypted link
  • No direct Internet redirection to VM300
  • Public origin, secure cookies, trust limited to the reverse proxy
  • Inspection of workflows and node types used

🌐 Active Internet publishing

The editor is published over HTTPS at n8n.stephanemuraro.fr (authenticated admin interface and webhook URLs produced by the instance), behind the VM200 reverse proxy. VM300's application port is not exposed directly: every public request passes through VM200, which terminates HTTPS, selects the service by the requested name, and relays only the intended routes. A later separation under a dedicated webhook name remains possible if a need for stricter exposure is confirmed.

🤖 Triggered by OpenCode — proof of concept (17 October 2026)

OpenCode triggered an existing, authenticated n8n workflow from two environments: a Windows workstation and the CLI of a dedicated Linux station (VM301). The agent uses its terminal tool to run a deterministic client; that client makes the HTTPS call and checks the expected reply (17 October 2026).

OpenCode → terminal tool → validation client → authenticated HTTPS webhook → checked JSON reply

  • Workflow with two linked nodes: Webhook (POST, Header Auth) then Respond to Webhook, which returns {"status":"ok","result":"OPENCODE_N8N_OK"}
  • On Windows, a call without authentication was refused (HTTP 403), then the authenticated call succeeded; this refusal was not tested separately on the Linux workflow
  • On both workstations, the real call through OpenCode's terminal tool returned OPENCODE_N8N_OK with exit code 0
  • Separate credentials for the two clients, kept out of Git
Difficulties encountered and resolution:
  • The full workflow must be run to test the chain up to the response node; merely receiving an event does not prove that chain.
  • On the Linux side, trials used an inconsistent authentication mode or credential; creating and selecting a new Header Auth credential gave a successful call.
  • The Windows client masks the secret and tells HTTP errors apart from response-format errors: a favourable HTTP status is not enough, the expected JSON fields and the exit code are also checked.
Exact scope: these are temporary test workflows, run manually in n8n to receive the agent's call. These trials validate no permanent endpoint, no automation with external effects, no automatic workflow creation, no Hermes integration, no MCP connection and no call to an n8n administration API. They are distinct from the n8n-to-Ollama workflow and from JSON generation by OpenCode. The local secret is not placed in the prompt, which is not isolation against a program running under the same account; exit code 0 is not a security audit. The workflow exports, operating scripts and call URL are not published.
⚙️ Operations automations (status as of 18 October 2026)

These two operations workflows are distinct from the temporary webhooks of the OpenCode proof of concept. They are launched by n8n without calling a model on each run: AI assistance intervenes in their preparation, followed by a review, corrections and human validation before publication. The story of that preparation appears on the VM301 page.

📡 HTTP monitoring every five minutes

A published workflow checks the HTTP responses of Ollama, OpenWebUI and Nextcloud, with no inference, restart or modification of the services. The manual and scheduled triggers use the same chain; the URLs are centralized in a dedicated configuration.

Each service produces a report: HTTP availability, response code, error category and timestamp. 2xx responses count as available; redirects are not followed. With no HTTP response, the conventional code in the report is 0. An error on one service does not prevent the other checks.

Observed validations:
  • three services returning HTTP 200;
  • connection refusal simulated without stopping the real service: error report, the other two results staying at HTTP 200;
  • the three checks back to HTTP 200 once the target was restored;
  • three successful automatic runs, five minutes apart.
Scope: the HTTP 503 and delayed-response trials are deferred: the local test target answered from the host but was not reachable from the container; the delays observed therefore do not prove validation of these two scenarios. The execution status Success means the workflow finished, not that every service is available: the reports must be read. No notification or automatic remediation is configured. This HTTP check demonstrates neither an LLM generation nor the success of a business operation in the applications.
💽 Disk capacity report on VM300

A second published workflow is configured to run every day at 08:00 Europe/Paris. The first automatic daily run is still to be observed; the validations available concern manual runs.

The collection covers the root filesystem of the application VM. Since n8n's local data and files share this filesystem, a single measurement avoids duplicates. PostgreSQL storage, hosted on another VM, is not covered.

Manual or daily trigger → restricted SSH → fixed collector → JSON validation → report

The dedicated account has no administrator rights. Its key enforces only the collector, with no terminal or port forwarding. The script is protected against modification by that account and uses the Python standard library, with no network, subprocess or configurable measurement path. The forced command was tested: another requested command produced only the authorized measurement.

The JSON distinguishes total capacity, used space, total free space, space available to an unprivileged user and reserve. The percentage accounts for that reserve and uses a ceiling rounding consistent with df for the tested filesystem; the local measurement matched df exactly, at 35% used during the check. The n8n report applies configurable thresholds: normal below 80%, warning from 80% and critical from 90%. The validation checks types, expected fields, relationships between sizes, the percentage and the timestamp; missing or inconsistent data produces erreur.

Available evidence:
  • 13 Python tests passing on Linux, including a real run of the collector;
  • manual measurement then SSH collection by n8n succeeded;
  • warning and critical states simulated without filling the disk, then simulation removed and back to the real measurement;
  • SSH refusal caused with a test port: erreur report, then back to normal once the configuration was restored;
  • daily publication confirmed, with no evidence of a first automatic daily run.
Scope: the report stays in the n8n execution results. No notification, deletion, cleanup or automatic disk extension is configured. The retention period of this history and the stability of access after the container is re-created are not validated by these trials; a prolonged SSH timeout was not tested. This workflow uses a Code node to validate and normalize the collector output; the manual review described above concerns the initial workflow to Ollama, where the absence of a code node was noted.
